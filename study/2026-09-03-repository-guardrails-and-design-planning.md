# 2026-09-03 TATATA 개발 운영과 디자인 계획 학습 기록

## 1. 제품 이해

### 핵심 정의

- **TATATA**: 한국어권 사용자를 위한 영어 타이핑 학습 서비스
- **영어 학습 우선**: 야구는 학습 결과와 성장을 보여주는 비유이며 제품의 목적이 아니다.
- **게임화**: 타석, 안타, 이닝, 시즌 기록으로 반복 학습의 동기를 만든다.
- **MVP 1**: 문서에서 합의된 최소 기능만 구현하고 범위를 임의로 넓히지 않는다.

### Source of Truth

- **기능 명세서**: 비즈니스 규칙의 기준
- **유저 플로우**: 화면 이동과 사용자 여정의 기준
- **승인된 디자인·와이어프레임**: 화면 구조와 시각 표현의 기준
- **최신 사용자 결정**: 기존 문서와 충돌하면 가장 최근의 명시적 결정을 우선한다.

### 공부할 것

- [ ] MVP와 기능 확장의 차이
- [ ] PRD, 기능 명세서, 유저 플로우의 역할 차이
- [ ] Source of Truth를 한곳에서 관리하는 방법
- [ ] 게임화가 학습 효과를 방해하지 않게 설계하는 방법

## 2. 핵심 학습 경기 구조

### 사용자 학습 루프

`단어 3개 학습 → 문장 타이핑 → 타석 결과 → 문법 복습 → 다음 타석 또는 이닝 결과`

- **단어 학습**: 철자, 뜻, 발음을 익히지만 공식 타석에는 포함하지 않는다.
- **문장 타석**: 공식 타석이며 정확도와 타이핑 속도를 측정한다.
- **타석 결과**: 정확도, 개인 평균 대비 속도, 난이도를 근거로 결과를 보여준다.
- **문법 복습**: 이해를 돕는 학습 단계이며 시즌 타율에는 포함하지 않는다.
- **이닝**: 3 OUT이면 종료하고 다음 이닝의 OUT은 0으로 초기화한다.

### 중요한 미결정 사항

- 안타 판정의 구체적인 threshold는 정해지지 않았다.
- 신규 사용자의 개인 평균 속도 기준을 만드는 방법은 정해지지 않았다.
- 정의되지 않은 수치를 코드에서 임의로 결정하면 안 된다.
- 초기 UI는 `PlateResult` 형태의 mock 또는 fixture를 사용한다.

### 공부할 것

- [ ] 상태 머신과 화면 전환 모델링
- [ ] 정확도와 WPM 계산 방식
- [ ] 절대 속도와 개인 평균 대비 상대 속도의 차이
- [ ] mock, fixture, production algorithm의 역할 차이
- [ ] 중복 제출을 한 번만 처리하는 idempotency

- 안타 결과

- 단어 상세

### 주요 전환

- 첫 방문자는 가입 없이 1이닝 체험을 시작한다.
- 회원은 진행 중 경기 여부에 따라 이어하기 또는 경기 설정으로 이동한다.
- 콘텐츠가 없으면 경기를 시작하지 않고 난이도나 카테고리를 다시 선택한다.
- 경기 종료 후 비회원은 기록 저장 가입 유도로 이동한다.
- 컬렉션에는 실제 학습으로 해금된 콘텐츠만 표시한다.

## 4. 디자인 재구성 원칙

### 시각 방향

- **핵심 키워드**: 야구 기록장, 학습 다이어리, 종이, 바인더, 티켓, 스탬프
- **색상**: 짙은 네이비를 기본으로 하고 빨간색을 주요 행동과 결과 강조에 사용한다.
- **레이아웃**: 좌측 사용자 요약, 중앙 핵심 학습, 우측 기록·도움말의 데스크톱 구조를 참고한다.
- **콘텐츠 우선순위**: 장식보다 현재 학습 과제, 입력 영역, 결과 근거가 먼저 읽혀야 한다.
- **브랜드 안전**: 실제 프로야구 구단·리그·선수의 로고, 유니폼, 마스코트, 고유 색 체계를 모방하지 않는다.

### 참고 이미지에서 가져오지 않는 기능

- Writing
- Short Passage
- Long Passage
- 코인 재화
- 확장 레벨 시스템
- 실제 경기 승패나 실제 구단을 연상시키는 요소

참고 이미지는 시각 언어만 참고하며 웹 유저 플로우에 없는 기능을 추가하는 근거로 사용하지 않는다.

### 공부할 것

- [ ] 디자인 레퍼런스와 기능 요구사항을 분리하는 방법
- [ ] 디자인 토큰: 색상, 간격, 타이포그래피, radius, shadow
- [ ] 정보 위계와 시선 흐름
- [ ] 데스크톱 화면의 3열 레이아웃과 반응형 축소 전략
- [ ] 저작권·상표권에 안전한 스포츠 테마 디자인

## 5. Repository Guardrails

### 핵심 Git 규칙

`1 Issue = 1 Branch = 1 Pull Request = 1 Commit`

- `main`에 직접 commit하거나 push하지 않는다.
- 최신 `main`에서 작업 branch를 만든다.
- 한 Issue에 관련 없는 변경을 섞지 않는다.
- Commit은 영어 Conventional Commits 형식을 사용한다.
- PR 제목과 본문은 한국어로 작성한다.
- 같은 Issue의 후속 수정은 가능한 경우 `commit --amend`를 사용한다.
- 원격 commit을 amend했다면 `--force-with-lease`만 사용한다.
- merge 후 작업 branch를 삭제한다.

### 오늘 적용한 흐름

1. Repository 상태와 원격 branch를 확인했다.
2. 개발 규칙을 `AGENTS.md`로 정리했다.
3. 한국어 PR 템플릿과 README 안내를 준비했다.
4. GitHub Issue #1을 생성했다.
5. `chore/1-project-guardrails` branch를 push했다.
6. 하나의 commit으로 PR #2를 생성했다.

### 공부할 것

- [ ] Issue, branch, commit, PR의 관계
- [ ] Conventional Commits의 type과 scope
- [ ] squash merge의 목적
- [ ] `git commit --amend`와 `git push --force-with-lease`
- [ ] `git fetch`, `git merge --ff-only`, `git rebase`의 차이
- [ ] working tree, local branch, remote tracking branch의 차이

## 8. 검증과 완료 기준

### 문서 작업 검증

- Markdown 구조가 탑다운으로 읽히는지 확인한다.
- trailing whitespace와 깨진 링크를 확인한다.
- `git diff --check`를 실행한다.
- 현재 Issue에 속하지 않는 파일이 포함되지 않았는지 확인한다.
- branch에 commit이 정확히 하나인지 확인한다.

### 기능 작업 검증

- 저장소에 정의된 lint, test, build 명령을 실행한다.
- 대상 화면과 주요 사용자 플로우를 수동 확인한다.
- 브라우저 console error가 없는지 확인한다.
- 비즈니스 규칙과 UI 문구가 기능 명세에 맞는지 확인한다.
